## Context

Handit 是通过 Markdown 指令和模板运行的跨 agent skill。仓库只有安装与静态校验脚本，没有可靠的后台事件处理器。现有 `SKILL.md`、`handoff-formats.md` 要求在多种执行事件后更新，`handoffprompt.md` 还通过“返回前更新”传递同类义务。只修改入口会留下旁路。

用户已经确定两项原则：自动写回发生在成功 commit 后，提交节奏即保存频率；handoff 不再维护下一步，因为它可能扩大用户意图并增加规划成本。仓库现有 OpenSpec 根用于承载本提案，不创建额外 handit 状态。

## Goals / Non-Goals

**Goals:**

- 两次提交之间不因执行进展而读写交接状态，也不循环判断是否“足够重要”。
- 对一次符合条件的成功提交至多执行一次集中更新，保持用户现有提交习惯。
- 从活跃格式与转交指令中移除下一步规划；保存已知事实及已有授权边界。
- 为触发、幂等、旧字段和隐性模板旁路提供可检查的验收场景。

**Non-Goals:**

- 不增加定时保存、token 阈值、每轮末保存、Git hooks、后台进程或旁观 agent。
- 不承诺强制中断前保存，也不自动追补其他会话的提交。
- 不改写用户正式 task/spec 中的计划，不取消显式 task 规划命令。
- 不解决所有 token 问题：完整引用文件的加载成本、记录永久保留和 light/full 分层另行设计。
- 不自动重装用户级 skill，不修改用户现有项目的 handoff，不自动提交或推送本变更。

## Decisions

### 1. 用已观察到的成功提交作为唯一自动触发事件

只有当前任务已有明确选中的 handoff，且当前 agent 从实际执行结果确认当前任务 commit 成功，才进入自动检查点。普通 commit 和显式授权的 amend 均可构成成功提交；失败、被取消、仅提出提交建议、push、checkout、pull 或历史浏览均不构成触发器。

不存在活跃 handoff 时不因 commit 初始化一个。交接对象不明确时跳过自动更新，不展开全项目 handoff 搜索。外部会话的提交由用户显式同步处理，不轮询 Git。当前任务所需的正常代码读取不受此限制。

这比“重要进展”“阶段完成”更容易判定；不引入每步或每轮重新评估的重要性判断。用户可以继续使用 `/tracehandoff` 或明确自然语言请求保存，包括未提交工作；仅说“暂停”并不自动等价于请求保存。

### 2. 一次提交对应一个有界检查点

在已有提交结果不足时，只读取该提交的 SHA 和变更路径来确认触发资格；不读取完整 diff 来重建工作日志。业务代码、正式文档或 task/spec 等当前任务交付物均可计为实质变更。仅修改当前交接根内执行 handoff、索引或历史记录的维护提交不触发。混合提交只要包含当前任务实质变更仍符合条件。

使用可选 frontmatter `checkpoint_commit` 记录最后一次成功自动写回对应的完整 SHA；初始化时缺省，手动同步保留该值，不能把未提交事实伪装成已提交。当前提交与标记相同则不重复写回或刷新时间。不同 SHA 的有效 amend 可创建新检查点。标记仅在相应 handoff 更新成功时写入；写入失败如实报告，不改写或回滚已成功的 Git 提交，不形成自动重试循环。

每个检查点仅最小更新选中 handoff；full 索引仅在所属行的事实状态变化时更新，保留现有最小编辑协议。需要记录的事实来自当前上下文和选中记录；允许沿用已有记录规则处理明确已被替代或解决的内容，但不能为决定记录去留额外调查、测试或扫描历史。

禁止为了保存 handoff 催促、创建、拆分、amend 或追加提交。写回之后即结束维护，不自动 stage、commit、push 或修改 ignore；本地/团队共享策略维持用户既有选择，因此共享 handoff 写回可能暂时形成未提交修改。

### 3. 手动入口与只读入口保持清晰

`/tracehandoff` 及明确的“同步/保存交接”请求可在没有提交时更新事实；无新增事实且无需用户指定更正时不为了更新时间而改文件。初始化、显式压缩、归档、学习记录等命令仍可执行其原本授权范围内的写操作，但其完成本身不额外触发检查点。

`/handoffprompt` 继续只输出 prompt。移除其对接收者“返回前必须更新”的要求，改为引用同一 commit/显式同步边界，不能把普通最终回复、阻塞报告或转交文本生成变成自动写回触发器。

### 4. 交接保存事实，不维护下一步

light/full 状态块只保留 `State` 和 `Blocked`。`State` 是已知当前情况；`Blocked` 是已知未解决障碍或 `none`，不是解决方案。允许记录已观察的验证结论及用户明确约束，不复制可从 commit、代码或 spec 直接恢复的实现细节，不为每次 commit 强制新增 Log 行。

索引 Active 保留 `Slug / Owner / Status / Updated`，Blocked 保留 `Slug / Owner / Blocker`，Done 保留 `Slug / Result`；移除 `Next Action`、`Needed`、`Follow-up` 等会继续承载行动规划的栏位。Archived 的归档时间、原因和实际替代记录引用仍属事实元数据。

`Scope`、已有验收定义和正式 task/spec 路径不属于推测的下一步，保持原本授权边界。转交 prompt 只能引用用户已指定的任务或正式工作项，不从 handoff 中生成新执行路线。明确请求的 `/inittask`、`/updatetask`、`/explorehandoff` 仍可履行规划职责，不能把其规划输出作为后台 handoff 下一步字段维护。

### 5. 旧数据按需兼容，不借迁移打断执行

旧 `Next`、`Next Action` 等内容在读取时视为非权威的历史建议；不得据此执行、刷新、复制到 prompt 或换名迁入其他字段。普通 commit 检查点不为删除它们发起额外迁移或历史保全流程。

新模板和当前示例完全移除这些字段；专门的 legacy 示例保留旧字段用于验证忽略行为。用户明确请求格式迁移或压缩时，才对选中记录移除旧规划字段；已经明确来自用户的约束应按其原来源保留，不能因字段移除丢失授权边界。没有获准迁移的其他记录与历史文件保持原样。

### 6. 验证行为边界，区分静态检查与实跑证据

两套 validator 检查统一的触发规则、当前模板无下一步字段、转交模板无无条件写回，并设置正反例：新模板若重新加入 Next 或“返回前总是更新”，校验必须失败。保留 legacy 输入以及正式 task/spec 计划的合法样本，避免全仓禁词误伤。

增加紧凑的场景验收说明：连续实现/失败/测试但未 commit 时自动 handoff 读取与写入均为零；有效 commit 后一次；重复 SHA、失败提交及 handoff-only 提交为零；明确同步可写；未知事实不触发额外调查。静态校验不能证明真实模型行为或节省比例。实现验证应使用隔离的临时 Git 仓库记录实际工具调用；没有实跑时明确标记未验证，不宣称 token 或任务质量改善已量化。

## Risks / Trade-offs

- [提交间进展可能丢失] → 接受检查点的时效边界，显式同步可保存未提交事实，不引入其他自动保存频率。
- [文本规则不能强制拦截所有 agent 行为] → 所有入口、引用和输出模板保持一致，以实际工具轨迹补充结构校验。
- [共享 handoff 在 commit 后变脏] → 保持既有 Git 授权，写回不自行提交；维护提交不形成触发循环。
- [已有历史体量仍然较大] → 本变更只缩减维护频率和规划职责，不宣称已经解决日志淘汰或冷启动开销。
- [旧版本接收者仍执行旧 Next] → 更新仓库内全部当前示例和转交模板；用户级安装作为独立发布动作处理。

## Migration Plan

1. 在仓库中统一更新 skill、命令、引用、当前示例和两套 validator；不触碰用户级安装副本。
2. 执行结构校验和隔离场景验收，记录实际执行与未执行的检查。
3. 用户决定发布或安装时，沿用现有安装流程更新 Codex/Claude Code；不把此动作包含在默认实现范围中。
4. 新建 handoff 使用新格式；旧 handoff 按兼容规则工作，仅显式迁移选中记录。
5. 回退时恢复仓库文件及对应安装版本；本设计不删除历史证据或改写用户 Git 历史。

## Open Questions

没有阻塞本提案实施的未定用户决策。运行时 hooks、量化 token 基准和记录淘汰策略属于后续独立讨论范围，不由本 handoff 变更生成或维护待办。
